# ADR 0022：任务执行信号作为 Phase A 的事实边界

- 状态：已接受
- 日期：2026-08-23

## 背景

Time Agent 已保存任务的预计时长、首次开始时间和完成时间，但没有记录暂停、恢复、跳过等执行证据。
没有这层事实，就无法可靠计算计划与实际差异，也不能在后续阶段校准个人估时或评估规划建议。

## 决策

在 `tasks` 领域增加不可变的 `TaskExecutionSignal`，保存用户明确产生的最小执行信号：

- `started`、`paused`、`resumed`、`completed`、`skipped`；
- 用户、任务、显式 UTC 发生时间、来源、可选结构化 metadata；
- 用户级 `idempotency_key`，重复提交返回同一信号，不重复产生事实；
- 所有写入经过 `TaskExecutionSignalService`，不得由 View、Tool 或前端直接写 ORM。

开始/恢复/暂停/完成信号在任务状态仍需要变化时复用 `TaskService` 的既有状态机；信号本身仍作为
独立审计事实保存。跳过只记录信号，不擅自把任务标为取消。

## 取舍

- 选择不可变信号而不是直接给 Task 增加一个“实际分钟数”，因为暂停/恢复和离线重试需要保留事件顺序，
  实际时长应由可重建信号计算。
- 先放在 `tasks` app，而不是创建新的 execution app，避免在数据量和消费方尚未证明前增加空抽象层。
- 本阶段不做后台定位、自动计时或从日历推断实际完成；只有用户明确操作才产生信号。
- 现有任务完成 API 保持兼容；新的执行信号 API 为后续 Web/Android 低摩擦操作提供幂等入口。

## 后续约束

计划/实际差异、估时校准和 benchmark 只能消费这些信号及 PostgreSQL 事实；Memory 和聊天记录不能替代它们。
如果未来引入外部执行来源，必须增加 Provider/source 语义和相应的权限、隐私、同步与审计设计。
