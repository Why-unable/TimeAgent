# 六、优先让 LLM 操作“语义决策”，而不是重新实现计算器

首先把 Planning 行为划分成：

```text
A. Deterministic Calculation
B. Hard Constraint
C. Heuristic Decision
D. Semantic / Preference Decision
E. User Decision
```

## 应继续 deterministic 的典型能力

例如：

* 时间加减；
* timezone / DST；
* overlap；
* Deadline hard constraint；
* work hours；
* free interval；
* Task/Event version；
* SchedulePlan TTL；
* Authorization；
* AutomationPolicy；
* idempotency；
* transaction；
* final apply validation。

这些应该作为 Tool / Service / Validator 暴露给 Agent。

LLM 不应重新计算这些事实。

---

## 优先研究由 Agent Harness 接管的能力

例如：

* 当前请求真正的 planning objective 是什么；
* 用户自然语言中的 soft constraints；
* Priority 和 Deadline 如何权衡；
* 哪些任务值得优先保护连续时间；
* 哪些任务适合碎片时间；
* 是否值得拆分任务；
* 哪些已有计划尽量不要移动；
* 多个合法 Slot 中哪一个体验更好；
* 容量不足时应该牺牲哪个任务；
* 用户近期行为和长期习惯哪个更值得参考；
* 是否需要询问用户；
* 当前 Plan 是否虽然合法但“不合理”；
* Replan 时应该采取什么最小破坏策略。

这些是真正值得利用 LLM Reasoning 的地方。

# 九、优先研究三类 Harness 模式

## 模式一：Planning Intent Agent

LLM 通过 Structured Output 产生：

```json
{
  "hard_constraints": [],
  "soft_constraints": [],
  "task_preferences": [],
  "planning_objectives": [],
  "tradeoffs": [],
  "questions_for_user": []
}
```

后续 deterministic Planner 消费该结构。

这种模式用于把：

```text
自然语言语义
→
结构化规划目标
```

交给 Agent。

---

## 模式二：Candidate Search + Agent Decision

Deterministic Engine 负责产生合法候选：

```text
Candidate A
Candidate B
Candidate C
...
```

Agent Harness 负责：

```text
观察候选
↓
结合当前目标
↓
结合 Memory
↓
必要时再调用 Tool
↓
比较 trade-off
↓
选择 / 要求生成新候选
```

不要只做一次 LLM Ranking。

允许 Agent：

```text
candidate
→ critique
→ request alternative
→ compare
→ select
```

形成真正的 agent loop。

---

## 模式三：Plan → Validate → Repair Loop

Agent 形成结构化计划：

```text
Planning Agent
↓
Schedule Candidate
↓
validate_schedule_candidate Tool
↓
violations
```

如果：

```text
violations != []
```

不要在 Python Service 中偷偷再次调用 LLM。

把 violation 作为 Tool Observation 返回 Harness：

```text
Agent
↓
看到违反 deadline / overlap
↓
重新 Reasoning
↓
生成 Repair
↓
再次 Validate
```

形成：

```text
Reason
→ Act
→ Observe
→ Repair
```

的 Harness Loop。

设置最大 iteration，避免无限循环。

# 十九、让 LLM 成为“策略探索器”

如果 Agent Harness 明显优于当前 heuristic planner，请进一步分析：

> **LLM 到底掌握了什么当前 Planner 没有编码的策略？**

例如可能发现：

```text
深度工作应该优先获得连续长 Slot

沟通类任务适合填碎片时间

容量不足时优先保护 deadline × importance 高的任务

Replan 应优先最小化对已有承诺的破坏

最近高负载时应该主动增加 buffer
```

然后区分：

```text
A. 能稳定形式化的规律
→ 下沉成 deterministic feature / objective

B. 很难固定表达的语义权衡
→ 保留在 Agent Harness
```

形成：

```text
Deterministic Baseline
        ↓
Agent Harness 探索
        ↓
Evaluation
        ↓
发现稳定策略
        ↓
沉淀成 Tool / Feature / Objective
        ↓
Agent 获得新的 Planning Primitive
        ↓
再次探索
```

因此 LLM 不只是运行时 Planner，也充当：

> **Planning Policy Discovery Engine**

# 二十八、必须进行“用户视角”的多轮 Planning Simulation

除了已有的确定性 Benchmark 和指标评测之外，本次任务必须增加一条独立的：

**User Perspective Planning Evaluation**

目标不是只判断：

```text
这个计划是否合法？
```

还要判断：

```text
如果我是这个用户，
我是否真的愿意按照这个计划执行？
```

因此，不允许只依赖：

* Hard Constraint Violations；
* Scheduled Minutes；
* Placed Task Count；
* Deadline Satisfaction；

这些确定性指标宣布 Planning 已经足够好。

必须增加从真实使用体验出发的评测。

---

# 二十九、使用子 Agent 构造“规划—评价—改进”闭环

如果当前 Coding Agent Harness 支持子 Agent / Subagent，请主动使用。

建议至少形成以下角色。

## 1. Scenario Agent

负责构造真实用户时间管理场景。

不要只生成简单的：

```text
3 个 Task
1 个 Event
```

而要生成具有真实权衡的场景，例如：

* 今天已经很累，但还有高优先级任务；
* 上午有连续会议，下午还有 Coding；
* Deadline 很紧但用户不希望晚上工作；
* 大任务与多个碎片时间冲突；
* 用户过去习惯上午深度工作，但今天上午有会议；
* 两个重要任务都无法完整安排；
* 临时会议导致原计划失效；
* 用户已经连续三天高负载；
* 某任务历史上经常严重低估；
* 用户明确说“今天轻松一点”；
* 用户希望“尽量不要把事情拖到晚上”；
* 用户希望“重要工作一口气做完”；
* 用户说“帮我合理安排”，没有明确给出所有 preference。

Scenario Agent 应生成：

```text
User Profile
Current Date / Time
Tasks
Events
Deadlines
Execution History
Relevant Memory
Explicit Preferences
Implicit Behavioral Evidence
Current Request
```

并给出 scenario_id。

---

## 2. Planning Agent Under Test

使用当前正在实验的 Agent Harness 进行真实 Planning。

必须尽可能走真实链路：

```text
User Request
→ Agent Harness
→ Tools
→ Planning Reasoning
→ Candidate
→ Validation
→ Repair / Critique
→ Final SchedulePlan
```

不要为了测试方便直接调用内部函数绕过 Agent Harness。

我们要测试的是：

> Agent 最终真实面对用户时能够产生什么结果。

---

## 3. User Simulator / User Judge Agent

这是最重要的新增角色。

让一个独立子 Agent：

> **站在这个用户的角度审查最终 SchedulePlan。**

它应该获得：

```text
用户当前请求
显式偏好
相关历史画像
Task / Event
最终 Plan
```

但不要告诉它：

```text
这个方案来自 Baseline
还是 LLM Variant
```

尽量做 Blind Evaluation。

User Judge 需要回答：

```text
如果我是这个用户，
我会不会接受这个安排？
```

并使用 Structured Output，例如：

```json
{
  "overall_satisfaction": 8,
  "would_accept": true,
  "would_modify": false,

  "scores": {
    "goal_alignment": 9,
    "priority_alignment": 8,
    "deadline_reasonableness": 9,
    "workload_balance": 7,
    "focus_continuity": 8,
    "fragmentation": 8,
    "preference_alignment": 9,
    "schedule_stability": 8,
    "realism": 8
  },

  "problems": [],

  "most_annoying_issue": null,

  "suggested_changes": [],

  "reason_codes": []
}
```

注意：

不要要求 Judge 输出隐藏 Chain-of-Thought。

只要求：

* 结构化评分；
* 简短理由；
* 问题标签；
* 修改建议。

# 三十、增加 Adversarial Planning Critic

除了普通 User Judge，再增加一个更严格的 Critic。

它不负责问：

> “这个方案合法吗？”

Deterministic Validator 已经负责合法性。

它主要攻击：

### 体验问题

例如：

* 一天塞得太满；
* 没有喘息时间；
* 高认知任务被拆得太碎；
* 深度任务安排在多个短 Slot；
* 低价值任务占据黄金时间；
* 明明可以少移动，却大范围 Replan；
* Meeting 前后安排重度任务导致切换成本过高；
* 用户明确不喜欢晚间工作却大量安排晚上；
* 连续多天高负荷；
* Plan 虽然能完成，但现实中执行概率低；
* 给用户安排得像机器，不像人。

### 决策问题

例如：

* Deadline 和 Priority 权衡不合理；
* 使用了低置信度 Memory 却忽略显式要求；
* 对历史行为过度拟合；
* Capacity 不足时没有主动舍弃低价值任务；
* 不应该拆的 Task 被拆分；
* 应该询问用户的时候强行替用户决策；
* 产生不必要的 schedule churn。

Critic 输出必须结构化。

# 三十一、同一个 Scenario 必须重复运行多次

由于 LLM Planning 存在随机性：

**单次表现优秀不能作为通过依据。**

对于关键 Scenario：

```text
同一个输入
```

至少重复运行多次。

例如：

```text
Scenario 01

Run 1
Run 2
Run 3
Run 4
Run 5
```

记录：

```text
Plan Quality
User Satisfaction
Hard Violations
Tool Trajectory
Model Calls
Latency
Token Cost
```

关注：

```text
平均表现
最差表现
方差
失败率
```

而不是只展示最好的一次。

如果：

```text
8/10
9/10
8/10
3/10
9/10
```

不能简单认为这个 Harness 是优秀的。

需要分析：

> 为什么偶尔会出现 3/10？

并继续迭代。

# 三十二、让子 Agent 做 Pairwise Blind Comparison

不要只让 Judge 给绝对分数。

对于：

```text
Baseline Plan
Variant Plan
```

随机打乱顺序后交给 Judge：

```text
Plan A
Plan B
```

问：

```text
站在该用户角度：

A 更好
B 更好
基本相同
```

并输出具体维度：

```json
{
  "preference": "A",
  "confidence": 0.82,
  "advantages": [],
  "disadvantages": [],
  "critical_difference": ""
}
```

不要告诉 Judge：

```text
哪个是 LLM
哪个是 deterministic
哪个是新版本
```

避免 evaluation bias。

# 三十三、不要只使用一个 Judge

如果资源允许，对核心 Benchmark 使用多个独立 Judge / Subagent。

例如：

```text
Judge A
用户满意度视角

Judge B
时间管理专家视角

Judge C
保守型用户视角

Critic
专门寻找计划缺陷
```

不需要所有场景都使用大量 Judge。

但关键 regression case 和最终候选 Harness 应进行更严格评测。

如果不同 Judge 分歧很大：

不要直接平均然后忽略。

分析：

```text
为什么存在分歧？
是不是用户偏好本身具有多解？
是否应该 ASK_USER？
```

这种“不确定性”本身可能就是 Agent 应该学习的能力。

# 三十四、引入“是否应该询问用户”指标

一个优秀的 Planning Agent 不是永远替用户做决定。

例如：

```text
今晚只剩 2 小时

A：
明天上午截止的重要报告

B：
用户明确承诺今晚完成的项目

两者都需要 2 小时
```

如果上下文不足：

优秀 Agent 可能应该：

```text
ASK_USER
```

而不是武断选择。

因此新增指标：

```text
Appropriate Clarification Rate
```

检查 Agent 是否能够判断：

```text
什么时候可以自主规划
什么时候应该根据证据做合理默认
什么时候必须询问用户
```

避免两个极端：

```text
什么都问用户
```

和：

```text
什么都替用户决定
```

```text
达到预期

Would Modify Rate
足够低
```

具体合理阈值由实验数据建立，但必须写出依据。

不要事先为了通过测试随意降低阈值。

---

## 3. Baseline Comparison Gate

Blind Pairwise Comparison 中：

```text
Final Harness
```

必须稳定优于当前 Baseline。

不能只在一两个 Case 上获胜。

---

## 4. Stability Gate

同一 Case 多次运行：

```text
不能偶发产生明显灾难性计划
```

关注最差结果，而不仅仅平均值。

---

## 5. Regression Gate

新增改动不得明显破坏：

```text
已有简单 Planning
Tool Calling
HITL
Memory
Replan
Latency
Cost
```

---

## 6. Cost Gate

如果为了：

```text
满意度 +0.2
```

引入：

```text
5 倍模型调用
10 倍 Token
8 倍延迟
```

应重新评估是否值得。

```text
Hold-out Planning Scenarios
```

要求包含：

* Deadline pressure；
* Overcapacity；
* Deep work；
* Fragmented availability；
* Memory personalization；

* Replanning；
* Ambiguous objective；
* Multi-day scheduling。

然后：

```text
Final Harness
vs

```

进行 Blind Pairwise Evaluation。

Coding Agent 必须查看：

```text

Judge 评价

```

逐 Case 审核。

如果仍存在明显：

```text

```

将该 Case 加入 Regression Suite，并继续下一轮。

# 四十七、最终验收标准的核心问题

在结束之前，不要只问：

> Benchmark 有没有提高？

而要问：

> **如果连续让这个 Agent 帮一个真实用户安排一周，我是否愿意把自己的时间交给它？**

具体检查：

```text
它是否理解我真正想完成什么？

它是否会保护重要工作？

它是否给我留出合理空间？

它是否会把一天切得支离破碎？

它是否过度使用历史偏好？

它是否能适应最近的变化？

计划坏掉以后它是否能稳定修复？

它是否为了“安排更多任务”而牺牲现实可执行性？

它什么时候会主动做决定？

它什么时候知道应该问我？
```

只有当：

```text
Deterministic Correctness
+
Planning Metrics
+
Multi-run Stability
+
Blind User Evaluation
+
Adversarial Critique
+
Hold-out Acceptance
```

整体都达到较高水平时，才认为本轮 Agent Harness Planning 迭代完成。

# 四十九、最终执行要求

不要只进行：

```text
开发
→ 测试
→ 完成
```

必须执行：

```text
审计当前 Planner

↓

构建 Agent Harness Variant

↓

调用 Subagents
生成复杂 Planning Scenarios

↓

Agent 多次真实排程

↓

Deterministic Validation

↓

Blind User Judge

↓

Adversarial Critic

↓

Failure Analysis

↓

修改 Harness / Tool / Prompt / Feature

↓

完整 Regression

↓

再次调用 Subagents 评测

↓

继续迭代

↓

Hold-out Final Evaluation
```

直到满足最终验收条件。

如果某轮结果没有改善：

回滚无效改动。

如果某种复杂 Harness 没有收益：

删除它。

如果最终实验表明某个 Decision 更适合 Deterministic：

将其下沉。

如果发现新的复杂语义 Decision：

保留在 Agent Harness。

目标不是让架构越来越复杂。

目标是：

> **让最终 TimeAgent 排出的日程，在严格满足时间约束的同时，越来越像一个真正理解用户的优秀私人时间规划助手。**
