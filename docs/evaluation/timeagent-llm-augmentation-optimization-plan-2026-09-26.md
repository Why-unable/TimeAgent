# TimeAgent LLM 增强优化方案

- 编制日期：2026-09-26（Asia/Shanghai）
- 依据：[TimeAgent 工具与多周时间管理场景实测](./timeagent-capability-and-scheduling-scenarios-2026-09-26.md)
- 状态：已完成 Agent harness 独立评审；待产品决策

## 一、决策摘要

本方案不把排程计算交给 LLM。建议让现有 Time Steward Agent 更好地理解多周计划的语义，把用户表达转换为明确的排程意图；由现有 Planning Service 生成、校验并持久化计划，再由 LLM 基于最终结果向用户解释。

优先做两件事：

1. 修正容量预测、候选生成与计划校验之间的工作日规则不一致。实测容量预测把周末算入工作容量，两个场景分别高估 18 小时和 54 小时；生成器也可能产生校验器会拒绝的周末候选。这是确定性正确性缺陷，应由代码修复，不需要 LLM。
2. 在现有 `create_agent()` 的工具调用中先承接按任务阶段划分的结构化时间窗；后续再评估如何支持“每周训练两次”“先完成章节复习再做模拟卷”等节奏和依赖语义。

后续再评估是否值得用 LLM 对多个已可行计划做软偏好排序。计划解释和未安排原因可以由现有 Agent 根据最终工具结果生成，但不得把建议说成已应用的事实。

## 二、问题依据

本次 10 个测试用户和 10 个独立会话均完成了草案、审批和应用闭环。最终写入的计划没有越过工作时间、截止时间或既有会议，也没有任务相互重叠；压力测试中容量不足的 5 项保持未安排。

体验问题主要出现在“硬约束有效、长期节奏不自然”：

- 四周训练的 8 项任务全部落在第一天，包括第二至第四周的训练。
- 四周备考的任务集中在前三天，缺少按考试阶段分布的复习节奏。
- 容量预测将周末作为可用工作时间；两个跨周场景分别高估 1,080 分钟和 3,240 分钟。
- Agent 曾声称生成了两个候选方案，但该轮没有调用 `compare_schedule_plans`；压力测试的早期口头建议也与最终未安排结果有一项不一致。

证据和逐场景记录详见[实测报告](./timeagent-capability-and-scheduling-scenarios-2026-09-26.md)。

## 三、现有 Agent harness 与职责边界

当前链路是 Chat API → Outer Graph → LangChain `create_agent()` → ToolRuntime → Application Service/Planning Service → PostgreSQL。`create_agent()` 管理模型和工具循环；Outer Graph 负责入口路由、handoff、中断恢复和确定性工作流。高风险的 `apply_schedule_plan` 通过 ActionProposal/HITL 审批后执行，审批恢复会继续原 AgentRun。实测普通闭环常见的两个 AgentRun，是先生成草案、用户再发确认消息触发应用提案；不是 HITL 审批本身必然新建一个 AgentRun。提醒派发由确定性 Celery Dispatcher 完成。相关实现见 [`time_steward.py`](../../backend/apps/agents/agents/time_steward.py)、[`planning_tools.py`](../../backend/apps/agents/tools/planning_tools.py)、[`PlanningService`](../../backend/apps/planning/services.py) 和 [`phase-6-action-proposal-hitl.md`](../architecture/phase-6-action-proposal-hitl.md)。

需要区分“LLM 调用了工具”和“工具内部计算由 LLM 完成”：当前模型会选择查询和排程工具，但容量计算、空档搜索、草案构造、校验、审批和写入均由业务服务或确定性状态机执行。

方案坚持以下边界：

- **LLM 负责语义**：提取阶段、先后关系、频次、用户偏好；信息含糊时提出简短澄清；依据最终结果解释计划。
- **业务服务负责事实**：计算容量和空档，执行截止时间/日历/工作日/间隔等约束，校验计划，应用经批准的变更。
- **审批保持显式**：模型理解用户意图不等同于用户授权写入；继续复用当前 ActionProposal/HITL。
- **定时执行保持确定性**：提醒和简报等既有工作流边界不因本方案改变。

## 四、优化设计

### 4.1 MVP：在现有工具调用中传递结构化排程意图

扩展现有排程输入，而不是新增一个 Planner Agent 或平行编排图。为控制 MVP 范围，第一小步只增加按 task ID 绑定的 `schedule_window`（该任务允许安排的起止区间）：Time Steward 从用户明确的阶段表达中提取时间范围，含糊时询问。它能阻止“第二周任务排在第一周”，但本身不保证同一周内训练均匀分散；产品不得把它描述为完整的周期排程。时间区间由用户明确日期或用户确认的阶段日期构成，并保存带时区的规范化值。

后续小步再按实际需求加入：

- 重复节奏：每周次数或任务之间的最小间隔；应给同一训练/学习系列明确的任务组身份，不应依赖标题字符串关联；
- 任务先后关系：例如模拟考试依赖章节复习完成；使用 task ID 关联；
- 每日负载上限、允许星期等偏好。明确提出的用户限制可作为硬约束，主观偏好先作为软偏好或澄清项。

Agent 应区分硬约束和软偏好。任务时间窗、任务依赖、工作时间和用户明确要求的频次属于必须验证的条件；“尽量均匀”“不要太累”先作为优化偏好，必要时询问用户，不可伪装成已保证的约束。

工具输出的草案快照应保存实际采用的结构化约束，确保后续 `validate_schedule_plan` 与 `apply_schedule_plan` 使用同一组计划意图。当前 `SchedulePlan` 已有 `constraints_snapshot` JSON 字段，可优先扩充版本化快照，避免仅为计划级约束新增表或迁移。Planning Service 对约束执行确定性处理；有任务无法满足时，返回未安排原因或需要用户决定的冲突，不得由 LLM 自行宣称计划有效。

首个版本可采用增量扩展现有 Tool Schema、`PlanningConstraints` 和 Planning Service。只有当约束必须作为长期任务属性被其他入口读取时，才增加 Task/API 持久化字段及对应迁移；若公开 API 有变化，按仓库规则同步 OpenAPI 和前端类型。不要为本功能创建无实际用途的抽象层或独立 Agent。

### 4.2 低成本增强：基于最终结果解释

复用现有 Agent 的最终回复能力，将已校验/已应用结果组织成简短回顾：

- 哪些任务已安排、哪些仍未安排；
- 每个未安排项对应的后端原因和可选下一步；
- 多周计划按阶段如何分布，以及用户表达的关键偏好是否被满足；
- 当前处于草案、等待审批、已批准还是已执行状态。

回复生成只使用工具结果、Proposal 状态和执行审计；没有对应工具证据时，不得声称“比较了多个方案”“已写入日历”或“计划可行”。

### 4.3 后续实验：对可行候选方案做软偏好排序

当前已有 `compare_schedule_plans` 生成两个确定性命名方案的能力，但它会创建两份草案，并不自动证明每份草案均通过最新校验；比较指标中的硬约束违规数也不能在确认实现真实计算前作为安全证据。将来开放候选比较时，需让比较服务在返回前对每个候选运行确定性校验，或要求 Agent 先校验两份计划并在校验完成前不做推荐；同时修正比较指标。不要先新增候选生成器。

若后续仍观察到用户频繁修改候选，可开展受限实验：先让比较服务只返回已通过校验的候选，并确保指标是真实计算；LLM 再基于候选数据和用户明确的软偏好说明取舍。优先复用 `create_agent()` 收到比较工具结果后的正常回复，不新增 ranker、Agent 或 Graph 节点。模型不能创造新时间块，也不能修改硬约束或绕过校验。评估工具调用、模型 token、用户选择质量和延迟；只有单独建立推理阶段时，才会增加一次专用模型调用。

### 4.4 暂不纳入

- 用 LLM 计算可用分钟、搜索空档、判断冲突或最终确认截止时间可行性。
- 用额外 Agent/Graph 重复实现 `create_agent()` 已承担的工具循环。
- 让模型直接写 Task/Event、批准 ActionProposal 或触发提醒。
- 在没有任务历史和估时反馈证据时，单凭模型猜测任务时长并自动排入日历。
- 默认对每个计划增加 LLM 质量审查调用；先修复已知周末规则漂移，并将周间隔、每日负载限制作为明确约束建模和验证。

## 五、实施顺序与交付切片

### 切片 A：确定性基线修正

修复容量预测、候选生成与排程校验之间的工作日规则漂移。`UserPreference` 当前有时区和每日工作起止时间，但没有一等的允许星期/例外日字段；`PlanningConstraints` 默认允许七天，计划生成沿用该默认值，校验却硬性拒绝周末。因此先明确产品规则并共用同一来源：默认按当前校验语义只允许周一至周五；若产品要支持周末工作，再设计显式用户设置及验证路径。容量、候选生成、validate 和 apply 必须使用一致规则。只修预测仍可能生成随后被拒绝的周末候选。此项不依赖 LLM，是后续效果评估可信的前提。

### 切片 B1：任务时间窗

在现有 Time Steward 工具调用中承接每项任务的允许时间窗，并将其写入带版本的 `constraints_snapshot`。Planning Service 在草案生成、再生成、编辑后校验及应用校验时一致执行。这个切片只承诺任务落在指定窗口内，不承诺窗口内周频率或每日负载均匀。

### 切片 B2：节奏和关联约束

评估重复任务最小间隔/周频次、任务依赖及每日负载上限；每次只新增已由使用场景验证的一类约束，并同步覆盖草案生成、再生成、编辑、validate 和 apply。现有 Agent 在信息缺失或矛盾时澄清。B1/B2 均不添加新 Agent、Outer Graph 分支或专用模型调用。

### 切片 C：结果解释与轨迹可靠性

更新提示和评测用例，让 Agent 只根据实际工具轨迹和 Proposal/应用结果陈述状态；场景要求比较却没有调用比较工具时，不能声称进行了比较。

### 切片 D：候选排序实验（可选）

先修正 `compare_schedule_plans`：候选返回前经过确定性 validate，硬约束指标来自实际校验。之后以影子评测或小流量实验验证现有 Agent 最终回复能否更清楚地呈现取舍并减少用户改动；量化工具调用、模型 token/成本和延迟。没有可量化收益则不进入默认路径。

## 六、成功指标与验收

以现有 10 个场景作为回归基线，并增加含模糊偏好和冲突约束的多周场景。模型是否能理解新约束仍是待验证假设：评测需逐项比对用户原话、Tool 参数、计划快照和最终时间块；含糊条件应观察是否澄清，不能只看回复是否自然。硬性指标：

1. 所有已安排任务满足当前切片已启用且用户明确/确认的硬约束，包括固定事件、用户工时、任务窗口、已实现的依赖/间隔、截止时间及频次；任何硬约束违规均为失败。
2. 容量预测与可排工作日的确定性计算一致；测试窗口中的周末不被计入工作日容量。
3. 对本版本承诺支持的跨周节奏，阶段/频次需在计划约束和最终 slot 中体现，而不是只出现在回复文字中；尚未支持的节奏应先澄清并明确告知。
4. 未安排任务及原因与最终计划记录一致；草案、待审批、已执行等状态描述与 AgentRun/ActionProposal/审计事实一致。

效率与体验指标：

- B1/B2 不新增独立模型阶段、Graph 节点或 Agent；常规请求在现有 `create_agent()` 工具循环中传递约束，可能略增输入/输出 token。歧义澄清会增加用户往返和对应 AgentRun；HITL 批准恢复沿用原 AgentRun。
- 相对当前的典型闭环，衡量 AgentRun 数和模型调用数；这次实测的两个 AgentRun 来自用户先看草案、再发确认消息，不应把它归因于审批恢复。
- 记录澄清率、用户修改/拒绝率、计划应用率、未安排原因分布、平均/第 95 百分位完成时延及每计划模型调用数。
- 对候选排序实验记录用户选择、后续修改、模型 token/成本和延迟；优先复用现有 Agent 收到 compare 工具结果后的最终回复来解释取舍，不增加专用排序模型调用。若另建专用推理阶段，必须单独证明收益；不以回复更长或主观“更智能”作为成功标准。

## 七、主要风险与控制

| 风险 | 控制方式 |
|---|---|
| LLM 将标题或阶段名误读成硬约束 | 仅把显式或用户确认的结构化字段作为硬约束；歧义时澄清；保存约束快照。 |
| Planning Service 不支持新语义，模型只在文字里“理解了” | 在功能验收中核对工具参数、计划快照和最终 slot，而不只读聊天回复。 |
| 比较工具创建了不可行候选或错误报告约束指标 | LLM 排序前逐个调用确定性校验；先修正/验证候选比较中的硬约束指标。 |
| 仅修容量预测仍保留生成/校验不一致 | 先定义星期默认规则和周末策略，用同一规则贯穿候选生成、容量预测、validate 和 apply，并做跨周末回归。 |
| 软偏好误压过截止时间/会议等规则 | 服务先生成可行候选并验证；LLM 只能对候选排序。 |
| 额外模型调用增加超时和费用 | MVP 复用现有 `create_agent()` 循环；额外排序只做有指标的可选实验。 |
| 草案与用户确认后的实际应用状态混淆 | 保持 ActionProposal/HITL；最终文案根据执行状态更新。 |
| API/存储改动扩大范围 | 优先扩展当前排程计划约束快照；确有跨入口持久化需求时再评估 Task/API 迁移。 |
| 比较后遗留未选草案 | 用户选择后明确保留选中计划并放弃未选草案，或定义过期清理策略；用审计记录结果。 |

## 八、方案结论

方案的核心增量不是“让 LLM 替代排程器”，而是让现有 Time Steward 把人类对长期节奏的表达转换成可验证的约束。最简路径是：**现有 `create_agent()` 理解并传入结构化意图 → Planning Service 生成/验证 → ActionProposal/HITL 应用 → 现有 Agent 根据最终事实解释。**

先修容量事实，再补充计划约束表达；候选 LLM 排序只有在真实用户指标证明有价值时才实施。

## 九、Agent harness 独立评审

评审对象是本方案草稿及仓库中的 `create_agent()`、Outer Graph、Planning Service 和 ActionProposal/HITL 实现。结论为**方向通过，实施前需控制切片范围并落实全生命周期校验**。

评审确认的优点：

- 复用 Time Steward 当前 `create_agent()` 工具循环，不新增 Agent、Outer Graph 分支或专用模型阶段。
- 普通请求可在已有 `propose_schedule_plan` Tool 调用中携带结构化约束；会增加少量 Tool Schema/context token。歧义澄清会增加对话往返；HITL 审批恢复继续原 AgentRun。
- `SchedulePlan.constraints_snapshot` 已是 JSON 字段，计划级约束可版本化保存，无需仅为此新增数据库迁移；现有快照构造函数需要接收并保存新约束。仅当约束成为跨入口长期 Task 属性时才扩展 Task/API。
- 容量、候选生成和验证须共用工作日规则；约束须贯穿生成、重生成、编辑后的 validate 和 apply 重验。
- 新增 Agent 自然语言意图映射需要做端到端测量：原话 → Tool 参数 → 计划快照 → 最终 slot；对歧义输入测试澄清行为。

评审还核实了候选比较边界：`compare_schedule_plans` 当前按两种排序创建并持久化两份草案，不会自动校验每份候选；`hard_constraint_violations` 指标目前硬编码为 `0`。因此，候选排序实验前要修正指标并逐项验证候选；优先让现有 Agent 的工具结果后续回复解释取舍，避免额外 ranker 调用。比较后还需处理未选草案的保留/放弃状态。

评审建议的最小高效实施路径：

1. 明确周末/允许星期产品规则，统一预测、生成、validate 和 apply。
2. 选择一个可端到端验证的多周语义切片。本报告选择按 task ID 指定的计划时间窗；再评估每周频次、间隔、依赖和每日负载，不一次性打包进 MVP。
3. 扩展现有 Tool Schema、`PlanningConstraints`、`PlanningService` 和版本化约束快照；不新增模型节点。覆盖生成、再生成、编辑、validate/apply。
4. 加入 LLM 映射评测和审计比对，确认模型提取的日期条件真正影响计划，而不是只体现在回答里。

详细评审意见已合并进上文的工作日规则、MVP 切片、比较候选和效率指标章节。

## 十、LLM 引导排程试验

- 追加试验日期：2026-09-27

### 试验设计

保留同一确定性排程器作为对照和执行器；对照组不传 `task_decisions`，实验组把 LLM 能从请求与可信上下文推导的阶段目标、任务前置关系和软偏好写入结构化 Tool 参数。Planning Service 只在这些意图范围内搜索真实空档，并在草案创建时及后续应用前复核任务版本、工作时段、事件/任务冲突、截止和硬约束。

| 场景 | 确定性基线 | Agent 决策进入草案后的结果 | 判定 |
|---|---|---|---|
| 四周 10 公里训练（8 项） | 8 项集中在同一个 ISO 周 | 8 项分布在第 42–45 周；全部已安排，创建时校验通过 | 有明确改善 |
| 四周认证备考（7 项） | 任务只占不超过 3 个不同日期，缺少明确阶段序列 | 至少占 6 个日期、覆盖不少于 20 天；范围梳理/学习先于首套模拟，错题补强先于第二套模拟，且依赖间隔通过校验 | 有明确改善 |
| 循环依赖的错误模型输出 | 不适用 | 服务在生成草案前拒绝依赖环 | 安全边界有效 |

另通过 `create_agent()` 的 scripted-model 集成用例验证：模型 Tool Call 中的 `task_decisions` 会进入 `SchedulePlan.constraints_snapshot`，偏好时间确实改变最终 slot，解释依据随计划项返回；没有直接更改 Task 或 Event 事实。

这些是隔离数据库上的固定任务和 Agent Tool 轨迹对照，不代表已经完成配置真实模型的十用户线上/端到端复测。当前环境未配置模型 API Key，因此没有产生外部模型调用、费用、真实模型 Token 或 p95 延迟数据。

### 从试验得到的排程职责划分

LLM 适合把用户用自然语言表达的“分阶段、先后顺序、间隔、倾向日期、已确认的约束”转换为按 task ID 绑定的决策；相比仅生成解释文字，这些决定被保存到草案快照并参与实际候选选择。模型建议的日期默认是软目标；硬日期窗只在用户明确给出或确认时传入。短 rationale 供用户理解安排依据，不存放私有推理。

服务继续负责可行性证明和事实写入：枚举用户时区的工作时段、避让既有日程和已占任务、校验截止/版本/依赖，拒绝循环或不满足的硬条件；高风险 apply 仍由 ActionProposal/HITL 把关。LLM 不应替代冲突计算、最终时段校验和写入服务，也不需要增加独立 Planner Agent 或第二个模型阶段。Agent `create_agent()` 的现有循环已足以读取上下文、提交结构化决策、查看验证结果并向用户解释。

本轮固化到排程链路的变化包括 `TaskScheduleDecision` 的带时区字段、软/硬约束语义、任务依赖和最小间隔；计划快照会保留这些值供再生成、复核和 apply 使用，创建响应同时返回确定性校验结果。决策字段的 Schema 描述明确提示模型软目标和硬约束的区别。

记忆方面，现有 `TimeMemoryMiddleware` 会在 Memory Policy 与用户设置允许时注入行为画像/语义偏好；规划提示将记忆当作软目标，不能升级为日期硬约束。该链路在代码中可用，但本轮没有种入不同用户记忆做排程 A/B，因此还不能声称记忆已改善这两个场景的安排质量；这应作为下一轮单独实验。

### 工具集与 Agent 可用性调整

Agent 注册表保持 44 个工具名：排程事实读取和空档查询共享 `get_planning_context` 的互斥 `context` / `free_slots` 模式。空档模式仅返回时区、时长和确定性可用时段，不把任务/日历标题等明细送入上下文；未给时长时用可信 Runtime 的默认日程时长。新 `availability` pack 让“这周找两个适合健身的晚上”等请求只暴露日期锚点与空档查询两个只读工具；多任务排程入口则保留 10 个与规划阶段有关的工具，并排除通用任务/日历 CRUD 和逐任务改期入口。模糊排程且只有建议意图时，只读模式会过滤草案与写入工具。

注册表数量没有因此减少：对用户请求更相关的目标是缩小每次调用暴露给模型的工具集，同时保留单项读写的原子业务操作和明确审批边界。后续只有在真实轨迹表明两项业务操作拥有相同语义、副作用和审批边界时，才适合合并它们；不建议合成跨日历、任务、提醒的泛化 `execute_action`。
