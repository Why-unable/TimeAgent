# TimeAgent 工具与多周时间管理场景实测

- 实测日期：2026-09-26（Asia/Shanghai）
- 代码版本：`c57fcd6`
- 实测入口：本机生产 Compose 栈，经容器内 Nginx `/api/v1/` 聊天接口；本机映射端口为 `7080`
- 测试范围：工具能力盘点，以及 10 个独立测试用户、10 个独立会话的端到端排程
- 计划窗口：2026-10-12 起，场景覆盖 1 周、约 2 周、3 周和 4 周

## 结论摘要

TimeAgent（下称 TA）的 Time Steward 注册了 **44 个唯一工具**：20 个只读/交接工具、24 个写工具。TA 能通过用户隔离的任务、日历、提醒、容量和排程服务收集事实；它能生成确定性的排程草案、按事件/截止时间/工作时间校验，并通过 ActionProposal/HITL 审批后应用。提醒发送由 Celery Dispatcher 确定性执行。当前外部日历工具只读取同步状态，不能在这组 Agent 工具中写入外部日历。

10 个会话最终均正常结束，共 21 个 AgentRun；所有 AgentRun 和 65 条 ToolAudit 均为 completed，10 个 ActionProposal 均为 executed。TA 生成并应用了 10 个排程计划；70 项场景任务中，**65 项写入计划时间，压力测试中的 5 项保留未安排**。只读 ORM 复核发现已排任务均未越过用户工作时间或截止时间，没有与固定事件或彼此重叠；70 条场景固定事件均未被 Agent 改动。

这表示 TA 已能完成“查事实 → 拟案 → 校验 → 用户确认 → HITL 审批 → 应用”的基本闭环。实测也暴露出两项明确的质量问题：多周任务经常被提前挤在最早的一至三天内；容量预测默认把周末也算作可用时间，因而会高估工作日容量。第 7 个用例把本应分四周执行的训练全部安排在同一天，虽无硬冲突，仍不符合实际训练节奏。

## 一、TA 的工具集合

### 1.1 当前运行注册表

注册表定义位于 [`apps/agents/tools/__init__.py`](../../backend/apps/agents/tools/__init__.py)；Time Steward 通过 [`create_agent()`](../../backend/apps/agents/agents/time_steward.py#L25) 接入这些工具。

### 1.2 整体能力与边界

- **以业务服务为操作边界。** Time Steward 由 LangChain `create_agent()` 构造；外层工作流负责路由、Briefing handoff、HITL 和中断恢复。工具经 Application Service/领域服务操作 PostgreSQL，不应直接改 ORM。
- **排程可重复校验。** 排程草案记录用户、任务版本、限制快照和有效期；`validate_schedule_plan` 根据最新事实检查，`apply_schedule_plan` 原子提交已校验的草案。高风险应用会建立 ActionProposal 并等待用户决定。
- **时间事实有时区上下文。** 本次东京用户场景能将东京本地计划和按上海时间登记的会议统一换算。TA 可以查询繁忙事件、任务截止时间及工作时间。
- **智能 Agent 不负责确定性派发。** Celery Dispatcher 负责定时提醒；Briefing 请求会 handoff，不应先经过 Time Steward 自行编排简报内容。
- **没有万能外部操作工具。** 44 个工具里没有 shell、文件系统或任意 HTTP 工具；外部日历在当前注册表中只有同步状态查询。
- **当前规划偏向尽早放置。** `propose_schedule_plan` 使用确定性 slot planner，硬约束包括已有事件、已有计划任务、截止时间和工作时间；它没有表达“在某周以后才可开始”“每周至少间隔几天”“每日专注时长上限”或训练递进关系的参数。排程结果可能全都合法，却不代表可持续或符合任务语义。
- **分类与风险策略仍有漂移。** `propose_schedule_plan` 被标作只读，但会持久化草案；`list_temporal_insights` 读取时可能扫描并更新洞察。HITL 风险策略还保留不在当前注册表中的旧 Event 名称 `create_event`、`create_event_batch`、`update_event`、`cancel_event`。详见[现有工具优化记录](../toolset-optimization/README.md)。

## 二、测试方法与审批流程

1. 为每个场景用 `AccountService.create_guest()` 建立一个独立、24 小时后过期的访客用户；只在创建用户的测试进程中临时覆盖 `GUEST_ACCESS_ENABLED=True`。部署配置仍为关闭，未开放公开游客入口。每个测试 Token 在流程结束时撤销，文档不保存 Token。
2. 通过认证 API 创建时区/工作时间、固定事件和待安排任务。完成 Guest workspace 自带的示例任务，避免它进入待排清单。除第 6 个东京场景外，时区为 `Asia/Shanghai`；标准工作时间 09:00–18:00，个别角色按场景缩短。
3. 每个测试用户创建一条新的 Chat Conversation。场景任务与事件先作为用户现有事实写入各自正式 API，然后经 Nginx 对聊天接口发送中文自然语言请求。每个场景一个会话；为走完 HITL，可在同一会话继续发送确认消息。
4. 读取 AgentRun、ToolCallAudit、ActionProposal、SchedulePlan 与最终任务计划时间，记录每个 AgentRun 的工具轨迹、状态和结果。Agent 对固定事件没有任何写工具调用；最终任务时间另行与日历事件、任务重叠、工作时段和截止时间核验。
5. 前 9 个场景在第一轮拿到草案后，测试用户在同一会话明确确认；TA 随后产生 `apply_schedule_plan` ActionProposal。测试程序只在提案计划里的 task_id 全属于当前用户该场景的既有任务时，才通过该用户的正式审批 API 批准，并等待原 AgentRun 恢复。第 10 个压力场景先明确优先级，再确认草案，因此有三个聊天 AgentRun。

初始请求遵循的共同意图是：查询已有日程和未安排任务；在明确日期范围和个人工作时间内按截止日期规划；保留固定事件；生成并校验草案；无法安排的项目保持未安排；经用户确认和审批后再应用。每个场景的具体边界和实际结果见下一节。

## 五、实测质量发现与改进建议

### P0：容量预测不遵守工作日约束

`[CapacityForecastService](../../backend/apps/time_memory/capacity.py#L50)` 用 `PlanningConstraints(max_results=10000, ...)` 调 `find_free_slots`，而 [`PlanningConstraints.allowed_weekdays`](../../backend/apps/planning/schemas.py#L16) 默认是 0–6。工作日偏好没有把周六、周日排除。因此容量预测把周末也作为工作时段计入，而排程校验器随后又会拒绝周末 slot（[`_slots_respect_constraint_snapshot`](../../backend/apps/planning/services.py#L917) 对 `weekday >= 5` 返回无效）。

实测场景 1 的范围有 10 个工作日和 2 个周末日，每天 540 分钟，固定事件共 450 分钟。容量工具算出 6,030 分钟，正好是 `(12 × 540) - 450`；若只算工作日应是 `(10 × 540) - 450 = 4,950`，高估 **1,080 分钟（18 小时）**。场景 2 的 26 天窗口含 6 个周末日：工具报 13,320 分钟；只算 20 个工作日并扣除 720 分钟事件应为 10,080 分钟，高估 **3,240 分钟（54 小时）**。

建议让容量预测与排程验证共享同一组明确的允许工作日/非工作日偏好，并增加横跨周末的容量 API 回归覆盖；不能只靠最终 `validate_schedule_plan` 兜底。

### P1：多周任务只按最早空档堆叠

测试 7 的“第一至第四周”训练全部在 10/12 完成；测试 2、8 的四周复习任务也全部落在 10/12–10/14。硬性截止、已有事件、任务冲突都通过了校验，但没有 `not_before`、阶段依赖或周间隔约束。自然语言标题里的“第二周训练”也没有被可靠转成下界条件。

建议在任务/规划输入中表达最早可开始日期、阶段依赖、每周频次/最小间隔和每日专注容量；不具备这些输入时，Agent 应先说明计划只满足硬约束，并避免把它描述成完整的四周训练节奏。

### P1：草案与 HITL 交互多一轮口头确认

前 9 个场景的首轮 AgentRun 已生成并校验草案，但通常以“请回复应用/请确认”作为正常文本结束，没有在同一轮生成 ActionProposal。测试用户回复确认后，才产生第二个 AgentRun 和 `apply_schedule_plan` 提案；正式 approve API 后，再恢复并完成写入。压力场景另有一轮优先级确认。

这是当前聊天交互的实际行为，不是计划已应用的证据。前端/用户必须等待提案状态或最终运行结果，不能把“草案已生成”当成“任务已经排入日历”。

### P1：模型会夸大或先说错，必须以审计/最终数据为准

- 场景 1 回复提到“两个确定性候选”，但工具轨迹没有 `compare_schedule_plans`。
- 场景 10 的第一次容量说明把一项 10/15 截止任务列入 10/16 时段；最终确定性草案识别了截止限制并将它标记未安排，最终数据库计划正确。

这说明自然语言回复不能替代工具证据或持久化结果。产品和评测应比较最终 ActionProposal/ToolAudit/任务计划状态，而非仅做文本判断。

### P2：工具风险清单与业务副作用需要统一治理

继续处理注册表和 [`risk_policy.py`](../../backend/apps/action_proposals/risk_policy.py) 的旧名称漂移，明确 `propose_schedule_plan` 这类“创建草案但不改 Task/Event”的副作用分类；为周末容量、阶段性跨周排程和容量过载建议补充 API/Agent 轨迹测试。当前实测未修改产品代码；本报告只记录实测和分析。

### 6.5 复测揭示的优化点

1. **工具包收敛没有阻止 Agent 循环超限。** #1、#9 重复查找空档/校验，达到 50 步上限，未进入用户审批。需要减少工具返回和循环次数，并给失败路径确定的退出答复。
2. **路由筛选与执行权限存在落差。** 用 #9 原始输入调用 `select_tool_names()` 没有选中排程工具包，但 ToolAudit 记录了 `propose_schedule_plan` 和 `validate_schedule_plan` 执行。当前 `ToolPolicyMiddleware` 过滤送给模型的工具列表，而 `create_agent()` 仍用全量 `TIME_STEWARD_TOOLS` 建立执行端；工具可见性筛选不足以充当执行时的权限检查。应在工具执行节点强制 allow-list，并增加“隐藏工具调用必须被拒绝”的测试。
3. **多周阶段和先后顺序仍没有转成规划约束。** #7 的四周训练压在一天内，#8 的模拟卷顺序倒置。标题和自然语言阶段没有转成 `not_before`、依赖或频率限制；多周计划仍只满足空档/截止日等硬约束。
4. **过载兜底正确，但重复草案留下脏状态。** #10 正确地把五项任务留空，但调用三次 `propose_schedule_plan`，最终多留一份未应用的 draft。应让审批和应用绑定唯一一份已校验计划，并处理重复草案。
5. **模型调用异常还不能诊断。** #2/#4 的审计仅有 `BadRequestError` 和耗时，不足以判断底层错误类别。应保存安全的结构化错误分类，避免记录密钥、认证信息或模型私有推理。

本轮只评估结构优化版本，没有修改产品代码或执行生产部署。原 7080 服务保持原状；本轮使用的 7081 隔离服务和数据库已在记录结果后清理。
